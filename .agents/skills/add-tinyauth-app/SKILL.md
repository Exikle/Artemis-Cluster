# Skill: Add Tinyauth Protection to an App

Gate an app behind the shared `tinyauth` forward-auth service (Pocket-ID OAuth, single shared
login/session across every protected app) instead of a per-app `SecurityPolicy.oidc` client.

**Before using this skill, confirm tinyauth is the right tool** — see the decision guide in
`.agents/references/identity-stack.md`. Short version: prefer `components/envoy-oidc` (native
Envoy OIDC, no extra dependency) for a single standalone app. Reach for tinyauth when you want a
shared login across several apps, or need authorization primitives Envoy's native OIDC doesn't
have (per-app group ACLs beyond simple allow/deny, IP rules, path rules).

Read `.agents/references/identity-stack.md` in full before proceeding — it covers the lldap →
Pocket-ID → tinyauth chain, the `ResourceSet` grant mechanism, and every gotcha found while
building this the first time (bazarr, 2026-07-14/15).

---

## Step 1 — Add the component to the app's `ks.yaml`

```yaml
components:
    - ../../../../components/tinyauth
    # remove ../../../../components/envoy-oidc if migrating an existing app off native OIDC
```

Also remove any existing `pocket-id-operator` dependency and `oidcclient.yaml` for that app —
tinyauth is the OIDC client now, not the app itself. Add a `tinyauth` dependency instead:

```yaml
dependsOn:
    - name: tinyauth
      namespace: security
```

## Step 2 — Grant the app's namespace access to the tinyauth Service

Gateway API requires an explicit `ReferenceGrant`, declared by the namespace that owns the
target resource (`security`, where the `tinyauth` Service lives) — it can never be declared by
the consuming namespace itself (that would defeat the point of the grant). This is generated by
a `ResourceSet` at `kubernetes/apps/security/tinyauth/app/resourceset.yaml` — **check its
`spec.inputs` list first**; if the app's namespace is already listed (e.g. `media`), skip this
step entirely, nothing to do. If it's a new namespace, add one line:

```yaml
spec:
    inputs:
        - namespace: media
        - namespace: <new-namespace> # add this
```

That's the only edit needed — the `ResourceSet` generates one `ReferenceGrant` per input, so
every app in that namespace shares the same grant. Do not create a new file or a new
per-app/per-namespace `Kustomization` — that was tried and reverted twice before landing on
`ResourceSet` (see `identity-stack.md` for why).

## Step 3 — Set the per-app group ACL

**Do not skip this.** Without it, _any_ user who can log into tinyauth at all gets access to the
app — tinyauth's group check defaults to allow when unset (`len(ACLs.OAuth.Groups) == 0` →
`EffectAllow`, verified against the pinned `v5.0.7` source). Add to
`security/tinyauth/app/helmrelease.yaml`, container env:

```yaml
env:
    TINYAUTH_APPS_<APPNAME_UPPERCASE>_OAUTH_GROUPS: <pocket-id-group-name>
```

The app name in the env var must match the app's subdomain (tinyauth derives the resource name
from the request's hostname, e.g. `bazarr.dcunha.io` → resource `bazarr`). The group value must
be the exact Pocket-ID group `name` (e.g. `app_admin`, underscored — not the hyphenated
`PocketIDUserGroup` CR name like `app-admin`).

## Step 4 — Test live before committing

Follow `.agents/skills/modules/test-and-commit.md`. Suspend root **and** `tinyauth` (**and** the
protected app's own Kustomization if it already exists), apply, then verify:

```bash
curl -sI https://<app-hostname>/ 2>&1 | head -5
# expect: HTTP/2 401, x-tinyauth-location header pointing at tinyauth's login
```

**The only reliable way to confirm the per-app group ACL actually works** is a negative test
against your own account (no second test account needed): temporarily set the group requirement
to a nonexistent group, confirm your own already-authenticated session gets denied, then set it
back to the real group and confirm access returns. A same-account positive-only test proves
nothing — it can't distinguish "correctly allowed" from "no ACL enforced at all."

## Gotchas

- **Per-app ACL is not automatic just because lldap has groups.** The group data genuinely flows
  lldap → Pocket-ID `groups` claim → tinyauth session (`ctx.UserContext.OAuth.Groups` is real),
  but tinyauth only _enforces_ it against a per-app requirement you explicitly configure. Splitting
  auth (tinyauth's own client) from per-app authorization (the `apps:` config) is the direct
  consequence of consolidating from N per-app OIDC clients down to one shared tinyauth client.
- **Tinyauth's Kubernetes label-based ACL auto-discovery only watches `networking.k8s.io/v1
Ingress`, not Gateway API `HTTPRoute`.** This cluster uses Gateway API exclusively, so that
  discovery path never fires — always use the explicit `TINYAUTH_APPS_*` env vars.
- **Runs as root.** `ghcr.io/steveiliop56/tinyauth`'s Dockerfile creates a `tinyauth` user but has
  no `USER` directive, so the image needs `runAsUser: 0` — skip the usual non-root H8–H10 review
  checks for this app.
- **No password login exists anywhere in this chain.** Pocket-ID is passkey-only
  (`"Pocket ID only supports passwordless authentication"`, upstream docs) — even for LDAP-synced
  users. lldap's own password (its self-service web UI, or the bind credential) never reaches
  Pocket-ID or tinyauth. Don't configure `TINYAUTH_USERS`/local accounts unless a genuine
  non-Pocket-ID login is wanted — it would be a second, unsynced credential store.
- **`v5.0.7` (pinned) has no `tinyauth config` debug command** — that's a newer release feature.
  Can't dump the live-parsed config to verify env vars landed correctly; rely on the negative-test
  method in Step 4 instead.
